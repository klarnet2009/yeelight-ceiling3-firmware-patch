# Модель безопасности и риски (`yeelink.light.ceiling3` / `YLXD17YL`)

Документ фиксирует криптографические свойства каналов связи, проверки целостности OTA-контейнера, правила обращения с локальными секретами и анализ рисков при прошивке светильника `YLXD17YL` (`yeelink.light.ceiling3`, `MT7697N`, сток `2.0.2_0048`).

---

## 1. Транспортное шифрование и аутентификация каналов

| Канал / интерфейс | Транспорт и порт | Конфиденциальность и целостность | Проверка подлинности / ключевые ограничения |
|---|---|---|---|
| Локальный MiIO (`otu`) | UDP `54321` | `AES-128-CBC` (PKCS#7), `key = MD5(token)`, `iv = MD5(key + token)`; целостность заголовка и payload через `MD5(head[:16] + token + payload)` (`Miio._crypt`, `FUN_100ff830`, `FUN_100ff906`) | Зависит от 128-битного `token` (хранится в NVDM `ot_config/token` и локально в `token.txt`). Защита от повтора — по полю `stamp`. При компрометации токена в LAN атакующий получает полный MiIO RPC |
| Облачный MiIO (`ots`) | TCP `443` (`ots.io.mi.com`) | TLS поверх `mbedTLS` (`d0_tls_open` @ `0x101024e4`, tls.c), поддержка X.509 CA и PSK (`mbedtls_ssl_conf_psk` с `DID`) | Взаимная привязка к `DID` и PSK (`ots_login_verify` @ `0x100fcd10`). Хостовые скрипты `xiaomi_qr_token.py` / `miio_ota.py` используют HTTPS с проверкой сертификата плюс прикладное `RC4` (drop-1024) + `SHA-1` на базе `ssecurity` |
| Yeelight LAN Control | TCP `55443`, UDP `1982` (`239.255.255.250`) | **Открытый текст (plaintext)** без шифрования (`FUN_100c3ee0`, `FUN_100c4ca4`) | **Без аутентификации.** Любой узел в локальной подсети может обнаружить лампу по SSDP и управлять ею по TCP `55443` (до 4 клиентов одновременно) |
| Загрузка OTA (`httpc_req`) | TCP `80` (HTTP) | **Открытый текст (plaintext)** при локальном OTA по `http://` (`FUN_100f8250` -> `httpc_req` @ `0x10100750`) | `FUN_100f8250` передаёт нулевой указатель root CA (`param_2[5] = 0`), поэтому HTTPS без root-сертификата не используется. Защита от случайного искажения — только `file_md5`, SHA-1 и CRC32 |

## 2. Целостность и отсутствие асимметричной подписи в MMM-контейнере

1. **Проверки контейнера MMM (проверено в `patch_ota.py`, `unpack.py`, `decomp/hal/arch_ota.c`):**
   - `bytes[0:4] == 0x004d4d4d` (`MMM\0`), `count == 3`;
   - `SHA-1` первых `136` байт заголовка сравнивается с полем `bytes[136:156]`;
   - `SHA-1` каждого сжатого LZMA-сегмента сравнивается с 20-байтным полем сразу после сегмента;
   - Замыкающий 4-байтный `CRC32` (полином `0xEDB88320`, начальное значение `0`, без финального XOR) по всему файлу без последних 4 байт проверяется функцией `arch_ota_check_crc` @ `0x100a8e78` (`FUN_100a7720` в `decomp/hal/arch_platform.c`);
   - В `miIO.ota` дополнительно передаётся `file_md5` всего файла.
2. **Отсутствие RSA/ECDSA-подписи в MMM-контейнере:**
   - Сам формат MMM **не содержит асимметричной криптографической подписи**.
   - В `decomp/miio/ota_app.c` (`app_fw_init` @ `0x100b1d74`, `app_fw_close` @ `0x100b1ee8`) и `decomp/miio/miio_ciphers.c` (`miio_signature_verify` @ `0x100ab7d8`) реализована проверка X.509-цепочки и подписи в конце образа (после `original_length`, начиная с сертификата перед `-----END CERTIFICATE-----`), но она выполняется **только если в параметрах `miIO.ota` выставлен флаг подписанного файла** (`*(char *)(param_2 + 0x38) != '\0'`).
   - Когда этот флаг сброшен (`*(char *)(param_2 + 0x38) == '\0'`), `app_fw_close` вызывает **только** `arch_ota_check_crc`, что и позволяет прошивать модифицированные образы без приватного ключа Xiaomi/Yeelight.
   - **Следствие для безопасности:** если злоумышленник имеет возможность вызывать `miIO.ota` (через скомпрометированный облачный аккаунт или локально после патча `0x100f831c` при знании `token`) либо подменить трафик HTTP на порту `80` в момент скачивания при известном `file_md5`, загрузка произвольного кода не заблокируется проверкой цифровой подписи.

## 3. Гигиена локальных секретов

- **`token.txt`:** содержит 32-символьный hex-токен устройства (`16` байт). Никогда не передаётся через CLI-параметры (во избежание утечки через историю команд и список процессов), хранится только в `token.txt` рядом со скриптами.
- **Секреты Xiaomi Cloud (`xiaomi_qr_token.py`, `miio_ota.py`):**
  - `userId`, `ssecurity` и `serviceToken` хранятся исключительно в оперативной памяти объекта `requests.Session` / переменных функции `login()` и не записываются на диск.
  - Файл `xiaomi_login_qr.png` содержит одноразовый URL входа с ограниченным временем жизни (~`300` с); после завершения входа его желательно удалять.
  - Метаданные `provenance.json` не содержат cookies или токенов сессии.
- **Исключение из системы контроля версий:**
  - Файл `.gitignore` в корне репозитория запрещает индексацию для `token.txt`, `xiaomi_login_qr.png`, журналов `flash.log`, `flash-step1.log`, `monitor_lamp.log` и любых временных дампов сессии.

## 4. Безопасность прошивки и остаточные риски

### 4.1. Обязательная промежуточная проверка `--stock`

- Перед прошивкой патченного образа выполняется сборка и локальная проверка тестового немодифицированного контейнера: `python patch_ota.py --stock` -> `yeelink.light.ceiling3-repacked-stock-2.0.2_0048.bin` (`segment-0 bytes changed vs stock: 0`).
- Это подтверждает целостность конвейера `liblzma-5.dll` (`LZMA1EXT`, `LZMA_MODE_FAST`, `LZMA_MF_HC4`, без EOS-маркера и short-rep символов), пересчитанных SHA-1 и замыкающего CRC32. Журнал `flash-step1.log` зафиксировал первую попытку раздачи этого образа на нестандартном порту `:8321`, позволившую выявить ограничение порта `80` в `httpc_req` (`0x10100750`).

### 4.2. Сохранение тёплой перезагрузки и OTA-канала

- **Тёплая перезагрузка (`yl_cache` @ `0x3ba000`):** патч `0x100bd942` (`yglc_network_monitor`: `efd1 -> 00bf`) убирает условие «свет выключен», позволяя сработать штатному `cmd.reboot` (`0x100f81e4`). Он сохраняет маркер `0xdeadbeef` (`type = 1`) и текущее состояние света в `yl_cache`, не увеличивая счётчик `fast_reboot_count` (лампа не сбрасывается в режим сопряжения при авторебутах).
- **Переподключение Wi-Fi (`0x100af298`):** замена `0bd9` (`bls`) -> `0be0` (`b`) принудительно выполняет `miio_wifi_stop()` + `lwip_net_stop()` без изменения учётных данных Wi-Fi в NVDM.
- **Сохранение OTA-восстанавливаемости:** оба патча не затрагивают подсистему OTA (`ota_app`, `arch_ota`, загрузчик) и сегменты `1` и `2`, поэтому после прошивки остаётся возможность как обновить патч, так и откатиться на исходный `yeelink.light.ceiling3-stock-2.0.2_0048.bin` по сети.

### 4.3. Обоснование патча `0x100f831c` (`do_ota`) и его риск

- В стоке инструкция `0x100f831a: lsls r3, r3, #0x1e` + `0x100f831c: 13d4 (bmi #0x100f8346)` в `do_ota` (`0x100f8304`) пропускает сброс запроса только при выставленном облачном бите; любой локальный запрос `miIO.ota` по UDP `54321` отклоняется с кодом `-30020` (`"ota is from local, droped"`).
- Патч `0x100f831c`: `13d4 -> 13e0` (`bmi -> b`) делает переход безусловным, разрешая локальный `miIO.ota` без облачного ретранслятора `--cloud=de` (исключается зависимость от облака Xiaomi для последующих обновлений/отката).
- **Компромисс безопасности:** расширяется локальная поверхность атаки — после установки патча любой узел в LAN, знающий `token`, сможет инициировать прошивку по UDP `54321`. Токен и локальная сеть должны оставаться доверенными.

### 4.4. Остаточные риски «окирпичивания» (bricking)

Несмотря на проверки в `patch_ota.py` и `miio_ota.py` (MD5 стока, identity rebuild, `parse()`, кратность 8 байтам, проверка размера сегмента `<= partition_length`, проверка отсутствия EOS-маркера, проверка `model == 'yeelink.light.ceiling3'`), сохраняются следующие риски:

1. **Потеря питания на этапе переключения/распаковки в загрузчике:** отключение питания в момент стирания/записи целевой области flash загрузчиком после перезагрузки приведёт к неполному образу и потребует аппаратного восстановления через UART/SWD.
2. **Отсутствие аппаратного WDT-отката (rollback) после старта нового образа:** по результатам анализа `decomp/WIFI_RECOVERY.md` аппаратный WDT не работает как периодический сторожевой таймер задач (используется только программный сброс `0x1209`). Если из-за ошибки в новом патче приложение сегмента `0` упадёт на старте (например, в `sys_assert : loop forever`) или не поднимет Wi-Fi/`otu`, автоматического отката к предыдущей прошивке не произойдёт.
3. **Интерактивная защита от случайной прошивки:** в `miio_ota.py` запуск без флага `--yes` требует подтверждения клавишей `Enter`, а прошивка без ручного подтверждения оператора запрещена.
